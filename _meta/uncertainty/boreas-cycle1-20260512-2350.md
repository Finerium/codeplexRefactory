## U1 (medium): Camera fly + OrbitControls handoff during tour interrupt

**Concern**: When user clicks on canvas mid-tour, the tour should pause/stop + restore OrbitControls. The cleanup path needs to (a) kill GSAP timeline, (b) flip `OrbitControls.enabled = true`, (c) sync `OrbitControls.target` to the camera's current lookAt vector so the next user drag does not snap. Edge case: if cleanup runs while a tween is mid-flight, the camera position is stale relative to OrbitControls.target. The damping factor 0.06 helps mask this transition but is not eliminated.

**Mitigation Wave 2**: On tour interrupt, animate OrbitControls.target.lerp(currentLookAt, 1.0) instantly + fire `OrbitControls.update()` once to commit. Restore enabled = true. Empirically test in smoke route.

**Confidence**: medium. Mitigation reasonable + smoke tested in Cycle 4. Not ferry-worthy.

## U4 (medium): Camera fly waypoint cameraOffset + lookAtOffset, what does the offset measure from?

**Concern**: Pythia `boreas-to-triton.md` says `cameraOffset: [x, y, z]` is "Camera position offset from building [x, y, z]" + `lookAtOffset: [x, y, z]` is "Camera look-at target offset". From which anchor? Building.position is `[x, y=0, z]` per Iris BuildingData (y is ground = 0). The building extends upward to `y = height`. Offset from `[building.x, 0, building.z]` (building base) or from `[building.x, building.height/2, building.z]` (building centroid)?

**Mitigation Wave 2**: Implement as offset from `[building.x, building.height/2, building.z]` (centroid). This means camera "flies to a point relative to building centroid" + looks at "a point relative to building centroid". Generic-30sec waypoints will use values like `cameraOffset: [20, 30, 30]` (camera 20 right, 30 up, 30 forward of centroid) + `lookAtOffset: [0, 0, 0]` (look at centroid exactly).

**Wave 3 reconciliation**: Document this convention in handoff to Triton. Triton's `building_context` may include `height` so future variants can compute richer offsets.

**Confidence**: medium-high. Convention reasonable + documented in handoff.

## U5 (medium): Drei <Html> portal vs sibling DOM overlay for HUD elements

**Concern**: Drei `<Html>` portal mounts DOM inside Canvas via React portal, automatically positioned in 3D space. Useful for "label sticking to a building". For full-screen HUD overlays (narration text, timeline scrubber, ending summary), <Html> with `fullscreen` + `transform={false}` is one path. Alternative: render HUD as ordinary DOM siblings of the Canvas element + position with absolute CSS.

**Mitigation Wave 2**: Use plain DOM siblings + absolute CSS for HUD. Reasons: (a) HUD elements need to be styleable with Tailwind utilities (Drei Html container shadows the styling tree), (b) keyboard accessibility easier with native DOM, (c) HUD elements are persistent (always-on while mode active) not 3D-anchored. Use Drei `<Html>` only if we want building-anchored labels in a future Boreas iteration.

**Confidence**: high (medium after second-guessing). Plain DOM siblings simpler + matches Designer cross-page glassmorphism pattern in Calliope MarketingShell.

## U6 (low): Wave 3 Demeter contract feedback, scrubberPosition translation to query window

**Concern**: TimelineState.scrubberPosition is 0..1. The query Boreas sends to Demeter `/api/activity` is `days: 30 | 60 | 90`. How does scrubber position translate into a query window? Option A: scrubber position is a "cursor" within the range, fetched data is the whole range, scrubber UI displays cursor-time on the rail. Option B: scrubber position dynamically slices the data range (e.g., last 7 days at position 0.5 of a 30-day range).

**Mitigation Wave 2**: Option A. Boreas fetches the full ActivityData for `rangeDays` once + the scrubber position is purely UI cursor highlighting the timeline marker most recent to the cursor. Smaller cognitive load + matches PRD "scrub last 30/60/90 days" wording (you scrub through, not slice).

**Confidence**: high. Wave 3 Demeter happy with this since query stays simple.

## U7 (medium): Hermes narration overlay timing, fade-in vs hard-cut per waypoint

**Concern**: Per Pythia contract, narration text fades in/out per `pauseDurationMs`. If pause is 3000ms, the fade-in should start at t=0 of the dwell + fade-out at t=2700ms (~last 300ms). Risk: if camera takes 2000ms to transit to waypoint, narration text could potentially overlap with the prior waypoint's outro. Sequencing: narration shows DURING dwell (camera arrived + stationary), NOT during transit.

**Mitigation Wave 2**: GSAP timeline emits `onUpdate` per waypoint phase. Narration state machine listens to phase transitions: `transit-start -> transit-end (= dwell-start) -> dwell-mid -> dwell-end -> next transit-start`. Narration overlay fades in at dwell-start + out at dwell-end. Boreas uses local React state set from GSAP callbacks.

**Confidence**: medium-high. Implementation simple + readable.
