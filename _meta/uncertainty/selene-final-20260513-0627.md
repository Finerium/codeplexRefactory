## Medium-confidence concerns

### M-1. Backend reachable from production frontend assumed, not directly verified

The hook `useDashboardData` calls `fetch(${NEXT_PUBLIC_API_URL}/api/dashboard...)`. In dev, `NEXT_PUBLIC_API_URL` is unset so the call resolves to `localhost:3000/api/dashboard` which 404s (no Next.js handler) and the mock fallback fires. This is the path I directly observed in the Playwright browser session.

What I did NOT directly verify in this cycle:
- The Atlas Kubernetes deployment at `https://duopoly.hackathon.sev-2.com` actually serves `/api/dashboard` with non-stub data (i.e. the `DashboardQueryService.fetch_dashboard()` returns rows from `mv_dashboard_velocity` etc., not the empty list defaults).
- CORS headers on the production FastAPI service allow the frontend origin (`https://duopoly.hackathon.sev-2.com` -> same origin, so should be fine, but no curl evidence).

Mitigation: the normalization shim `normalizeBackendDashboard()` overlays backend fields onto the mock baseline, so even a partial response (e.g. backend returns kpis but no milestones) yields a fully-populated dashboard with mock fill for absent fields. Worst case is the panitia see Wave 1 mock numbers instead of a hard error.

### M-2. MilestoneProgressPanel data source is mock-backed in dev

`DashboardData.milestones` is populated by:
- Mock branch: `mockDashboardData.ts` ships two hardcoded milestones (Manager dashboard v1 72%, OpenSpec dual-folder 90%).
- Real branch: `DashboardQueryService.fetch_dashboard()` in `backend/app/services/dashboard_query.py` line 129 declares `milestones: list[MilestoneProgress] = []` (empty list default). The query that populates it from Postgres is NOT shown in lines 105-145 of the service file I read; it may exist further down or it may genuinely return an empty list until a Demeter cycle wires the GitHub milestones table join.

Risk: in production, the milestone panel may render the "no active milestones" empty state if Demeter has not wired the Postgres query. Mock fallback in dev hides this.

Mitigation: the empty-state branch in `MilestoneProgressPanel` is graceful ("no active milestones for this scope") and does not error. If Demeter ships the query post-this-cycle, the panel will auto-populate. If not, the panel surfaces an honest gap rather than a broken panel.

## Low-confidence concerns documented for context

### L-1. MilestoneProgressPanel inline styles vs CSS module

The new component uses inline `style={{ ... }}` props for layout (grid, gap, color tokens). The dashboard convention is CSS module classes (e.g. `styles.card`, `styles.cardBody`). I chose inline styles for time budget: refactoring the styles into the .module.css file would require adding maybe 12 new class names + cross-referencing them. The visual output is correct; the convention violation is real but cosmetic.

### L-2. `milestoneOverdue` + `milestoneAtRisk` classes are speculatively defensive

I added two CSS classes to the dashboard module for severity tinting. They are applied conditionally in the component (`rowSeverityClass()` helper). The mock milestones in `mockDashboardData.ts` happen to have `daysRemaining: 3` and `daysRemaining: 1` with 1 blocker + 0 blockers, neither of which triggers either severity class. So my Playwright snapshot did not exercise the severity branches. The branches are wired and CSS is in place; they just have not been visually demoed.
