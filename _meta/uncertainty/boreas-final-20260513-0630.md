## U3: Slice intensity computation runs per-render MEDIUM

**Concern**: `computeSliceIntensities` in HotspotGlow.tsx loops over `data.timeline` (30 days * ~30 commits per day = ~900 entries for 30d window) on every scrubberPosition change. At 60fps scrubber drag this is 900 * 60 = 54k ops/sec. Risk: noticeable jank on lower-end devices during drag.

**Mitigation**: useMemo dependencies = [data.timeline, scrubberPosition, rangeDays]. Only recomputes when one of these changes. scrubberPosition step=0.001 means 1000 distinct positions max, but in practice drag fires ~60 changes/sec. 900-entry loop is single-pass map aggregation, sub-millisecond on modern hardware.

**Action**: trust the useMemo perf. If Pan demo flags jank, add a debounce on setScrubberPosition (50ms) to throttle re-render rate.

## U5: Burst building tied to nearest marker assumes marker buildings cover hot buildings MEDIUM

**Concern**: HotspotGlow burst building uses `findNearestMarker` on data.timelineMarkers. If the user scrubs to a position with no marker within 1 day, burstBuildingId is null and no burst halo renders. The "city visual scrub commit-by-commit" effect would still work via the slice intensity but lose the burst pulse cue.

**Mitigation**: 116 markers spread across 30d means ~1 marker per ~6 hours on average -> generous 1-day window almost always finds a match. Verified via smoke script: all 5 test positions found a nearest marker.

**Action**: acceptable.
